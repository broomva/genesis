Genesis · design spec · revision 3

Realtime voice, wired to the workspace session

A voice you can interrupt, that dispatches real work into your Genesis session and narrates it while it runs — without pretending the voice model is the agent doing the work.

Revision 3. Two rounds of cross-model adversarial review, 2/10 then 3/10. Round 1 found that the spec built its narration design on an event stream that does not reach the browser at all — true, and worse than the reviewer could see. Round 2 found that four of revision 2's own fixes were contradictions in their own right: a cost control that killed the channel it was funding, a requirement whose mechanism had been deleted while fixing something else, a sequence number promoted to a "correctness" it cannot deliver, and a subsystem that would have broken the text UI to ship a voice feature. This revision fixes those. The review ledger, with every disposition, is at the foot of the document.

The problem this exists to solve

WhatsApp gave us a channel but a poor instrument: turn-based, no interruption, and a reply that arrives whole. The obvious next step — "add speech to the PWA" — splits into three designs that are not interchangeable, because in Genesis the session is the context. A session binds a workspace, owns a worktree, and carries agentSessionId for --resume continuity. Anything that does not ride the same threadId is a different agent with a different memory.

OptionFeels realtimeIs the workspace agentVerdict
A — voice as an I/O skin on /api/chatnoyesContext free, but a turn can take minutes of silence
B — realtime agent with tool accessyesnoFast, but you are talking about the session, not to it
C — realtime front, async dispatch, narratedyesbothThis spec. Two agents, one honest about which is which

C is not a compromise between A and B — it is the recognition that a conversational partner and a long-running worker are different roles, and the interesting engineering is the channel between them. Revision 1 treated that channel as a detail. It is the product.

The channel does not exist yet

Revision 1 claimed this was "buildable here specifically" because packages/session-host/src/ir.ts defines a typed event stream — tool.use, tool.result, permission.request, awaiting, turn.complete. Those types are real. What is not real is any path that carries them to a browser.

Here is what a subscriber can receive today. This is the output of grep -rn "hub.publish" --include="*.ts" apps packages at 8cc05ff — a static sweep, so it establishes that no lexical call site publishes anything richer, not that none could exist behind an indirection:

// apps/api/src/server.ts — the ONLY three hub.publish call sites
:638   hub.publish(threadId, { kind: "turn", role: "user",  text })
:640   hub.publish(threadId, { ... })
:647   hub.publish(threadId, { kind: "turn", role: "agent", text, phase })

// apps/api/src/hub.ts — the transport behind them
"Minimal per-thread pub/sub for the live /ws stream …
 Phase 5 replaces this with a durable bus; Phase 1 keeps it in-memory."

Three consequences follow, and each one killed a piece of revision 1:

  • Granularity. The wire carries turns, not tool calls. A narration policy keyed on tool.use and tool.result has nothing to read. Revision 1's phase 3 would have produced a well-tested pure function with no input.
  • Durability. Hub is an in-memory fan-out with no cursor and no buffer. A browser that sleeps, backgrounds, or reconnects loses every event emitted while it was away — including the final result. The file's own comment concedes this.
  • Authorization. GET /ws?thread=… has no auth gate at all, and the thread id is caller-supplied.

So the first phase of this project is not voice. It is an event channel worth subscribing to — and the text UI wants it just as much, because the PWA cannot show live tool activity today either.

Architecture

Two things changed shape from revision 1. The event channel is now a named subsystem with a sequence number, a replay cursor and an auth gate — not an arrow. And events land in the browser, not at the vendor: narration is a client-side projection, so the policy is unit-testable without a microphone and every payload passes through code we own before it is sent. That buys inspection and redaction before the send — it is not a privacy boundary, and the section below says so.

The load-bearing assumption — and it is still an assumption

dispatch_to_workspace is a client tool that fires the dispatch and returns within milliseconds — { accepted: true, runId, summary: "dispatched to broomva/genesis" }. Nothing is held open, so nothing depends on an undocumented vendor timeout. That part is sound.

What revision 1 asserted and could not support is the next sentence: "the conversation continues normally." Returning a tool result hands control back to the model mid-turn, and every realtime API this design could sit on will generate something at that point. The honest statement is:

ClaimStatus
A client tool can return in milliseconds without a held-open callsound — it is our own code that returns
Returning the result does not itself produce a spoken turnunverified — measured in phase 0
A contextual update delivered mid-generation reaches the current utteranceunverified — measured in phase 0
A superseded update cannot influence audio already generatedfalse — supersede is forward-only by construction

The last row matters more than it looks, and revision 2 drew the wrong conclusion from it. is_superseded can only affect what the model reads next; it cannot retract a stale progress note that has already shaped an in-flight sentence. Revision 2 responded by claiming "correctness comes from the sequence number" — but a sequence number cannot unspeak audio either. Nothing available to this design can retract an utterance already being generated.

So the seq rule is an ordering and suppression rule, not a correctness one:

  • The projection drops any event whose seq is not greater than the highest already narrated for that runId — strictly greater, so a replayed boundary event is not spoken twice.
  • After a run's terminal event, every further progress event for that runId is dropped unconditionally.
  • The high-water mark is persisted per runId in sessionStorage, so a page reload does not re-narrate a replayed window.

What that buys is a bounded staleness, stated plainly: at most one utterance may be in flight when a later event supersedes it. A progress note can therefore still finish playing after the result has arrived. The design does not pretend otherwise; the screen carries the authoritative state, and the dock marks the run complete the moment the terminal event lands regardless of what is still being spoken.

Session lifetime — the channel must outlive the button

Revision 2 added "releasing the button must end the session, not just mute it" as a cost control and thereby destroyed the feature. The entire point is that you speak, the work runs for minutes, and the result comes back — so a session that dies on button release has nothing left to speak with by the time the answer arrives.

StateMicElevenLabs session

Push-to-talk gates the microphone, which is what the user is anxious about; the session is what narration needs, and it closes on a timer. Cost is bounded by the cap, and the case where the cap bites is a specified degradation with a visible affordance rather than an unexplained silence.

Narration policy — three things take a turn, everything else informs

Revision 1 contradicted itself here: it routed turn.complete to a result context id while also promising "the actual answer, spoken". A contextual update informs the model; it does not make it speak. Delivered that way, the answer would sit silently in context until the user happened to say something else. The rule is now explicit:

EventSpoken asDelivery
tool.use"reading handler.ts", "running the tests"contextual update · progress
tool.result isError"the tests failed — three in whatsapp-format"contextual update · progress
thinking— dropped, but see below —none
turn.completethe answerturn · sendUserMessage
error"it failed: <message>"turn · sendUserMessage
heartbeat (synthetic)"still working, about ninety seconds in"contextual update · progress

"Takes a turn" now names an operation. Revision 2 stated the requirement and deleted the mechanism. The mechanism is sendUserMessage — the SDK primitive that injects a turn and therefore causes speech. Two things follow. Its exact name and behaviour are a phase 0 measurement, not a settled fact, because a design that cannot make the agent speak on demand has no terminal delivery at all. And delivery can fail: if the session is gone or the call errors, the result is already on screen and the dock marks it ready, not spoken — a visible, recoverable state rather than silence the user must guess about.

Dropping thinking is not the same as saying nothing. Revision 1 dropped it to avoid sounding like it was stalling, and thereby created the silence it was trying to avoid: a worker can reason for minutes before its first tool call. The dock therefore runs a timer — not the pure projection, which only ever sees events — and synthesises a heartbeat event after 45 seconds of silence on an active run, then every 60 seconds, capped at four. The text is derived from elapsed time and the count of events seen, never from the content of the reasoning. It is delivered as a contextual update, so it informs without interrupting, and it stops the instant a real event or the terminal event arrives.

Length and safety are two rules, not one. Revision 2 collapsed them into a single 600-character threshold, which made length decide whether a hostile or secret-bearing string got spoken. They are now independent:

  • Safety, applied first. The result text goes through the same redaction and delimiting as every other payload, and is always handed over as a delimited quotation, never interpolated into the instruction region. A payload that trips a redaction pattern is not spoken at all — the agent says the answer is on screen.
  • Length, applied second. Under 600 characters the agent delivers the quoted text; above it, it says what happened and points at the screen. Reading a diff aloud is useless, and "use judgement" is not a policy a test can hold.

Everything on this channel is untrusted text

Revision 1 claimed narration is safe because it is "a projection with a fixed vocabulary" and because results are "quoted, not paraphrased". Both are false in the part that matters. The vocabulary is fixed only for the frame; the payload is file paths, tool inputs, error strings and the agent's own output — arbitrary text from a workspace that may contain anything, including instructions aimed at whatever model reads it next. And quoting does not bind a language model: a correct quotation can be wrapped in a confident, wrong spoken claim.

  • Payloads are truncated and delimited, never interpolated into the instruction region of an update.
  • The web agent's prompt is written to treat all event payloads as data to be reported, never as instructions — and that instruction's effectiveness is a measurement in phase 0, not an assumption.
  • Everything the projection forwards is shipped to a third-party vendor. A redaction pass (known token shapes, absolute home paths, .env contents) runs in the projection rather than as a later hardening step — but it is pattern-based and therefore incomplete. A secret with no recognisable shape, pasted into a file and echoed by a tool, will pass through it. The design reduces exposure; it does not eliminate it, and a workspace holding material that must never reach a vendor should not have voice enabled.
  • The voice-agent-config.test.ts pattern extends to the web agent: CI fails when the prompt starts promising capabilities the system does not have.

This does not make the voice model trustworthy. It makes the blast radius bounded and the failure legible: the screen always holds the authoritative record, and the spoken layer is explicitly a narration of it.

What must be built

0
Protocol spike — the real go / no-go. One day, throwaway, against the live ElevenLabs agent. Measures, in order of how badly a wrong answer hurts: (1) does returning a client-tool result produce a spoken turn? (2) does a contextual update delivered mid-generation reach the current utterance or only the next? (3) under a burst of ten updates on one contextId, what does the model actually see? (4) can a contextual update alone ever cause speech, or is a turn always required for the result? (5) does the prompt-level "treat payloads as data" instruction hold against a hostile string? Then — and only then — (6) iOS getUserMedia in the installed PWA and whether capture forces speaker output.

Revision 1 made (6) the whole gate. A no-go there changes an affordance — push-to-talk, headphones, a text fallback. A no-go on (1)–(4) changes the architecture. The spike must fail in the order that matters — and "changes the architecture" is not a decision, so each answer has a consequence written down before the measurement is taken:

If the measurement says……then
(1) returning a client-tool result does force a spoken turnSurvivable: the tool returns a one-clause acknowledgement worth speaking ("on it — dispatched to genesis"). Only if the forced turn cannot be kept short does Option C fail.
(2) a contextual update reaches only the next turnProgress narration is dead as designed. Fall back to short turns via sendUserMessage at a fixed cadence — noisier, still useful. Re-score before building.
(3) a burst on one contextId is not deduplicated as documentedThe dock rate-limits to one update per 5s and coalesces itself. Cheap; no architectural change.
(4) sendUserMessage cannot reliably cause speechOption C fails. There is no terminal delivery, and the honest fallback is Option A — voice as an I/O skin, with the answer read on completion.
(5) the "payloads are data" instruction does not hold against a hostile stringResult text is never spoken verbatim; the agent reports type and length and points at the screen. Degrades the feature, does not kill it.
(6) iOS forces speaker outputAffordance change only: headphone guidance, or desktop-first launch. Not a gate.
1
The event channel. The bulk of the work and the part with value independent of voice. Emit IR-granular events from the print engine into a per-thread EventLog that stamps every event with a monotonic seq and with the runId the dispatch carried, retains a bounded window in memory, and serves GET /threads/:id/events?since=<seq> so a reconnecting subscriber resumes rather than restarts. Additive, not a swap. The PWA's live chat feed consumes Hub's {kind:"turn"} schema today; replacing it outright would break the text UI to ship a voice feature. So EventLog is new, and Hub's three existing messages are re-published from it by an adapter that keeps the old shape byte-identical. Hub retires only after the PWA moves to the new stream, in its own change. Gate the new surface: the BFF route authenticates and checks thread ownership, and the engine's /ws stops accepting an unauthenticated caller-supplied thread id.

Replay has a shape, not just a query. ?since=<seq> is exclusive. The window is bounded at 500 events or 30 minutes per thread, whichever is smaller. A cursor older than the window returns { gap: true, from: <oldest> } rather than a silent partial history, and the dock narrates a gap as "I lost track of the details — here's where it is now" after reading current run state. Catch-up and live-tail are one operation, not two: the subscription is opened first and buffered, the backfill is served into it, and only then is the buffer drained — so an event emitted between the two cannot fall down the crack.

2
POST /api/voice/dispatch. Sibling of /api/chat. Accepts { threadId, text, runId }, authorizes the principal against that thread, forwards, returns immediately. The runId is generated by the client, because an idempotency key must exist before the request it protects. The server records it on first sight and returns the original outcome for any repeat, so a retry after a lost response cannot run the work twice; it is also what ties an event stream back to the utterance that caused it. One active run per thread: a dispatch arriving while a run is in flight is rejected with a distinct code, and the agent says so rather than starting a second worker in the same worktree.
3
A second ElevenLabs agent, as code. Separate from the phone agent: different trust model, different prompt, different tools. Extends integrations/elevenlabs/ and inherits the provisioning script and the prompt regression test.
4
<VoiceDock> + the narration projection. A pure function narrate(event, state) → {kind:"context"|"turn"|"drop", text, contextId} carrying the seq/terminal rules from the section above, unit-tested against recorded event fixtures including out-of-order and post-terminal arrivals. The React surface is thin; the policy is testable without a microphone.
5
Dogfood. Drive a real task by voice in a scratch workspace: ask for a change, hear it work, hear the result. Kill the network mid-run and confirm the reconnect resumes from the cursor rather than going silent. Capture the ElevenLabs transcript alongside the event log and diff what was said against what happened — the spoken claim against the tool.use sequence and the final diff.

What this deliberately does not do

No permission-answering by voice

Revision 1 scripted "answer a permission prompt by voice" as a dogfood step. There is no permission round-trip to answer: the print engine has no permission protocol, and the interactive engine auto-allows (apps/api/src/index.ts:243). Building the voice half of a handshake whose other half does not exist is how a spec becomes a description of software that never shipped.

No cancelling the worker by voice

Barge-in stops the voice agent. It does not stop claude -p — the only abort path in the tree kills an interactive session on thread delete (supervisor.ts:1170). Until the engine grows a mid-run cancel, "interrupt it" means interrupting the narration, and the spec says so rather than implying otherwise.

No AI SDK 7 upgrade

The web app is on ai@6.0.213; realtime there is beta and would put a major-version migration on the critical path of a feature that does not need it.

No change to the phone agent

Different trust model, different prompt, different failure modes. They share a vendor and a provisioning discipline, nothing else.

On authorization, plainly: authorizePrincipal authenticates a human session or a machine token. It does not check that the principal owns the thread, and no route does today — the deployment is single-owner, which is why nothing has broken. Voice adds a browser-driven endpoint that takes a thread id, so this stops being theoretical. The ownership check is phase 1 work and is listed there, not waved at here.

Round 2 — what it caught that round 1 could not. Four defects were introduced by revision 2's own fixes, and that is the finding worth recording: (i) a push-to-talk cost control that ended the session narration needed; (ii) "takes a turn" kept as a requirement after its mechanism was deleted; (iii) the seq rule promoted to "correctness" when it cannot retract an in-flight utterance any better than supersede can; (iv) "replaces Hub" ignoring that the text UI consumes it. Also upheld: length and safety collapsed into one threshold; a privacy claim the browser boundary does not deliver; a runId assigned in two places; an in-tree claim stated more strongly than the grep that produced it. Reframed rather than accepted: the reviewer's merge condition was an end-to-end prototype passing adversarial tests. That is a request for the artifact this document exists to authorise, not a defect in it — which is why phase 0 now carries a decision table binding each measurement to a named consequence, including the one that fails Option C outright.
