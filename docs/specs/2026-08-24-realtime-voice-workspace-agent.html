Genesis · design spec

Realtime voice, wired to the workspace session

A voice you can interrupt, that dispatches real work into your Genesis session and narrates it while it runs — without pretending the voice model is the agent doing the work.

The problem this exists to solve

WhatsApp gave us a channel but a poor instrument: turn-based, no interruption, and a reply that arrives whole. The obvious next step — "add speech to the PWA" — splits into three designs that are not interchangeable, because in Genesis the session is the context. A session binds a workspace, owns a worktree, and carries agentSessionId for --resume continuity. Anything that does not ride the same threadId is a different agent with a different memory.

C is not a compromise between A and B — it is the recognition that a conversational partner and a long-running worker are different roles, and the interesting engineering is the channel between them.

Why this is buildable here specifically

Genesis already emits the exact material narration needs. packages/session-host/src/ir.ts defines a typed event firehose per session:

session.lifecycle · message.user · message.assistant · thinking
tool.use · tool.result · permission.request · permission.resolved
status · turn.complete · awaiting · error · unknown

That is not a log — it is a semantic stream. tool.use carries a name and input ("running the test suite"), permission.request carries a tool name ("it wants to write outside the workspace"), awaiting means the agent is blocked on you. Narration is a projection of this stream into speech, and the projection already has a home: packages/projection/ turns these events into UI parts today.

The decisive factor is not raw capability — all three could carry audio. It is that ElevenLabs is already reviewed infrastructure here: a provisioned agent, two webhook tools, integrations/elevenlabs/ config-as-code, a provisioning script that survived a live 422, and apps/api/src/voice-agent-config.test.ts which fails CI when the prompt starts promising things the system cannot do. A second vendor would duplicate all of it.

The one feature that decides the architecture is sendContextualUpdate with contextId: progress updates that inform the agent without taking a turn, and where a later update supersedes an earlier one instead of accumulating. A minutes-long agent turn emits dozens of events; without supersede semantics the voice model drowns in stale context.

Architecture

The load-bearing decision: the tool returns immediately

OpenAI's realtime docs specify no timeout for a tool response and say nothing about whether the session may speak while a call is pending. ElevenLabs' server-tools docs are equally silent on long-running jobs. Building on an unspecified behaviour is how you ship something that works in a demo and dies on a real ten-minute test run.

So dispatch_to_workspace is a client tool that fires the dispatch and returns within milliseconds — { accepted: true, summary: "dispatched to broomva/genesis" }. The conversation continues normally. Everything after that arrives as contextual updates. No held-open call, no dependence on vendor timeout semantics, and barge-in keeps working because the agent is never blocked.

Narration policy — a projection, not a firehose

IR eventSpoken ascontextId
tool.use"reading handler.ts", "running the tests"progress (superseded)
thinking— suppressed —n/a
tool.result isError"the tests failed — three in whatsapp-format"progress
permission.requestinterrupts — "it wants to write outside the workspace. Allow?"via sendUserMessage
awaitinginterrupts — "it's waiting on you"via sendUserMessage
turn.completethe actual answer, spokenresult
error"it failed: <message>"result

thinking is deliberately dropped: it is long, high-volume, and narrating it makes the agent sound like it is stalling. Progress shares one contextId so only the newest survives — the voice model should know where the work is now, not everywhere it has been.

Two events use sendUserMessage rather than a contextual update, because they must take a turn: a permission request and an awaiting block are the two cases where the system genuinely needs the human, and a non-interrupting update would leave them waiting in silence.

What must be built

0
Spike: iOS mic + audio routing — go / no-go
Half a day, throwaway. Confirms getUserMedia in the installed PWA and measures the known iOS behaviour of forcing output to the speaker once capture starts. If voice means speakerphone-only on the target device, the product decision changes before any code is written.
1
A second ElevenLabs agent, as code
A separate agent from the phone one — different trust model (an authenticated PWA session, not a spoofable caller id), different prompt, different tools. Extends integrations/elevenlabs/ and inherits the provisioning script and the prompt regression test.
2
POST /api/voice/dispatch in the BFF
Sibling of /api/chat, reusing authorizePrincipal unchanged. Accepts { threadId, text }, forwards to genesis, returns immediately. The threadId is what binds voice to the existing session — same workspace, same worktree, same resume.
3
<VoiceDock> + the narration projection
A pure function narrate(irEvent) → {kind:"context"|"turn"|"drop", text, contextId}, unit-tested against recorded event fixtures. The React surface is thin; the policy is testable without a microphone.
4
Dogfood loop
Drive a real task by voice in a scratch workspace: ask for a change, hear it work, interrupt it, answer a permission prompt by voice, hear the result. Capture the session transcript plus the IR trace and diff what was said against what happened.

What this deliberately does not do

  • No AI SDK 7 upgrade. The web app is on ai@6.0.213; realtime there is beta and would put a major-version migration on the critical path of a feature that does not need it.
  • No change to the phone agent. Different trust model, different prompt, different failure modes. They share a vendor and a provisioning discipline, nothing else.
  • No speech synthesis of the agent's raw output. Reading a diff aloud is useless. The voice agent speaks about the work; the screen shows the work.
  • No second source of truth. Voice dispatches into the same thread the text UI uses. There is no voice-only history to reconcile.
